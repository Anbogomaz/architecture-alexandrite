Проектная работа 4 спринта: "Александрит"
Задание 2: Выбор и настройка мониторинга в системе

Мотивация:
- Сейчас отсутствует технический мониторинг всех критичных компонентов
- Бизнес получает информацию о проблемах только от клиентов или партнёров
- Без метрик невозможно понять, где узкие места и как меняется нагрузка
- Мониторинг необходим для построения алёртов, виджетов и последующего анализа

Выбор подхода:
- Для API-сервисов предлагаю использовать метод RED (Rate, Errors, Duration)
- Для RabbitMQ и системных ресурсов — метод USE (Utilization, Saturation, Errors)
- Также предлагаю использовать Prometheus как источник метрик, Grafana — для визуализации

Выбранные метрики:

- Number of requests (RPS) for internet shop API
  Зачем: позволяет отслеживать общее количество входящих запросов
  Ярлыки: method, endpoint, status_code

- Number of requests (RPS) for MES API
  Зачем: позволяет выявить всплески нагрузки со стороны API-партнёров
  Ярлыки: client_id, method, status

- Number of HTTP 500 for CRM API
  Зачем: помогает контролировать ошибки со стороны сервиса
  Ярлыки: endpoint

- Response time (latency) for MES API
  Зачем: отражает задержки в ответах и деградации
  Ярлыки: method, endpoint

- CPU % for MES API
  Зачем: позволяет отслеживать загрузку инстанса
  Ярлыки: instance_id

- Memory Utilisation for shop db instance
  Зачем: при достижении лимита возможны сбои
  Ярлыки: db_name

- Number of connections for MES db instance
  Зачем: помогает выявить проблемы утечек соединений
  Ярлыки: instance_id

- Number of dead-letter-exchange letters in RabbitMQ
  Зачем: отслеживание потерь сообщений
  Ярлыки: queue_name

- Number of messages in flight in RabbitMQ
  Зачем: сигнализирует о перегрузке системы
  Ярлыки: exchange, routing_key

План действий:
- Развернуть инстанс Prometheus
- Настроить экспортёры для API, RabbitMQ, баз данных
- Настроить сбор RED и USE метрик
- Развернуть Grafana, подключить Prometheus как источник
- Настроить дашборды для ключевых метрик
- Настроить базовые алёрты (e-mail или Slack-интеграция)

Показатели насыщенности:
- CPU > 85% в течение 5 минут
- response time > 3с у MES API более чем у 10% запросов
- dead-letter > 20 сообщений в минуту в RabbitMQ
- подключено более 80% от максимально допустимого числа соединений к базе

Действия при превышении порогов:
- Отправка алёрта в Slack и по почте
- Создание тикета в трекинг-системе
- При критическом уровне — автоматическое масштабирование или рестарт
