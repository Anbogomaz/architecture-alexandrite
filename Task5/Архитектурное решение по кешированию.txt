Task5: Архитектурное решение по кешированию

Раздел: Мотивация

- Операторы жалуются на медленную загрузку первой страницы MES — дашборд заказов.
- Даже после внедрения пагинации и фильтров загрузка всё ещё занимает значительное время.
- Проблема возникает из-за отсутствия кеширования тяжёлых запросов к базе MES.
- Кеширование списка заказов ускорит работу операторов, повысит их мотивацию и снизит нагрузку на БД.
- Также можно снизить общее время отклика системы, повысить отзывчивость интерфейса.

Раздел: Предлагаемое решение

- Тип кеширования: серверное
- Паттерн кеширования: Cache-Aside
- Причины выбора Cache-Aside:
  - Гибкий контроль кеша со стороны приложения
  - Позволяет кешировать только актуальные запросы
  - Не требует синхронной записи в кеш
- Не выбираем Write-Through, потому что это приведёт к лишней нагрузке на кеш при записи
- Не выбираем Refresh-Ahead, так как он избыточен для простого списка заказов

Операции для кеширования:

1. Чтение списка заказов:
   - При запросе MES сначала проверяет Redis
   - Если данные есть — отдаёт их
   - Если данных нет — запрашивает из БД, кладёт в Redis и возвращает

2. Обновление статуса заказа:
   - Запись в БД
   - Удаление записи из Redis (инвалидация по ключу)
   - При следующем запросе будет кеширован уже актуальный список

Используемая технология кеша:

- Redis — in-memory хранилище с поддержкой TTL и инвалидации по ключу

Стратегия инвалидации кеша:

- Тип: инвалидация по ключу
- При любом обновлении/изменении статуса заказа, связанный ключ кеша будет удалён
- При следующем чтении данные обновятся и снова будут закешированы

Дополнительная стратегия (для редких кейсов):

- Временная инвалидация TTL — например, 5 минут
- Это обеспечит автоочистку кеша даже в случае редких изменений

Сравнение стратегий инвалидации:

По ключу:
- Позволяет точно обновлять только нужные данные
- Минимальный риск устаревших данных
- Лучше подходит для операций с чёткой логикой обновления

TTL:
- Гарантирует автообновление даже при ошибках в логике инвалидации
- Может вернуть устаревшие данные при слишком длинном TTL
- Используется как страховка

Sequence Diagram (словесное описание):

1. Пользователь (оператор MES) отправляет запрос на просмотр заказов
2. MES проверяет наличие данных в Redis по ключу "orders:list:status=X"
3. Если данные есть — Redis возвращает их → MES отрисовывает
4. Если данных нет — MES делает запрос к базе MES
5. База возвращает список → MES пишет его в Redis с TTL → отдает оператору

При изменении статуса:

1. MES обновляет статус в БД
2. MES удаляет кеш по ключу "orders:list:*"
3. При следующем запросе список будет заново сформирован и закеширован

Обработка ошибок инвалидации:

- Если запрос на обновление статуса был прерван:
  - данные в Redis могут остаться устаревшими
  - при критичности можно задублировать удаление кеша асинхронно в фоне
  - также можно использовать TTL в 1-3 минуты как защиту от зависших кешей

Вывод:

- Такое решение даст ощутимое улучшение скорости отклика
- Cache-Aside прост в реализации и хорошо масштабируется
- Redis легко масштабировать и внедрить без серьёзных изменений в код
