Проектная работа 4 спринта: "Александрит"
Задание 3: Архитектурное решение по трейсингу

Мотивация:
- В текущей системе заказы часто теряются на одном из этапов
- При возникновении ошибки невозможно отследить цепочку действий
- Партнёры жалуются на пропажу заказов, внутренние операторы — на отсутствие прозрачности
- Внедрение трейсинга поможет быстро определить, где и почему "завис" заказ

Системы, которые нужно покрыть трейсингом:
- MES API (особенно расчёт стоимости)
- CRM API (статусы заказов)
- Online-магазин (инициация заказов)
- RabbitMQ (перемещение сообщений между системами)

Данные, попадающие в трейсинг:
- trace_id и span_id
- путь запроса (endpoint, метод)
- статус ответа (HTTP status)
- длительность каждого span
- таймстемп начала/конца запроса
- мета-данные заказа (order_id, customer_id)
- ошибки/исключения (если есть)

Предлагаемое решение:
- Использовать OpenTelemetry SDK в каждом из сервисов
- Добавить экспортеры в OpenTelemetry Collector
- Развернуть Collector как отдельный компонент
- Настроить отправку данных в Jaeger (all-in-one)
- Настроить Jaeger UI для визуализации
- Протокол передачи: gRPC/HTTP
- Настроить генерацию trace_id и propagation между сервисами
- Интеграция с RabbitMQ через middleware (для trace propagation)

Дополнительное задание. Автоматический мониторинг процесса прохождения заказа и алертинг
Для реализации автоматического мониторинга прохождения заказа через трейсинг и настройки алертов предлагается следующая схема:
- Источник данных: OpenTelemetry Collector будет собирать спаны от всех микросервисов, включая данные о статусах заказов (инициация, подтверждение, расчёт, производство, упаковка, доставка).
- Метрики и правила алертов:
  - Если заказ задерживается на любом этапе более 30 минут, формируется алерт (анализируется duration_ms в спане и текущий статус).
  - Если заказ не продвинулся по статусу в течение 1 часа, срабатывает событие "подозрение на зависание".
  - Если после PRICE_CALCULATED не поступил MANUFACTURING_STARTED в течение 10 минут, формируется предупреждение.
  - Если в трейсах зафиксированы ошибки (error = true) на ключевых этапах (SUBMITTED, PRICE_CALCULATED, MANUFACTURING_COMPLETED), создаётся уведомление.
- Инструмент визуализации: Jaeger используется для детального анализа спанов, агрегированные данные экспортируются в Prometheus.
- Алертинг-система:
  - Используется Alertmanager, интегрированный с Prometheus.
  - Настраиваются шаблоны уведомлений для технической поддержки (например, email, Telegram или Slack).
  - Возможно подключение к системе тикетов (например, JIRA) для автоматического создания задач при критических инцидентах.
- Реакции на алерты:
  - Оповещение DevOps-инженера и тимлида.
  - Заведение тикета, если инцидент повторяется.
  - Возможна повторная публикация сообщения в очередь RabbitMQ или активация fallback-сценария (например, отправка уведомления клиенту о задержке заказа).



Дополнительные компоненты:
- Alertmanager (если на основе трейсов будут алёрты)
- Интеграция с Grafana Tempo (опционально)

Безопасность:
- Доступ к Jaeger UI только по VPN или с авторизацией
- Разграничение прав доступа: только разработчики и поддержка
- Исключение чувствительных данных из трейсов 

Компромиссы:
- Возможно, невозможно полноценно внедрить трейсинг в стороннюю MES
- Внутренние вызовы RabbitMQ могут потребовать значительной доработки
- Частота и глубина трейсов могут повлиять на производительность
