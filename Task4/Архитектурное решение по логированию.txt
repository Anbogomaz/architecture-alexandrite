Task4: Архитектурное решение по логированию

Раздел: Мотивация

- В системе отсутствует централизованное логирование, из-за чего разбор ошибок происходит по обращениям клиентов. Это увеличивает нагрузку на поддержку и замедляет устранение проблем.
- Логирование поможет быстрее находить причины нестабильной работы сервисов, понимать, где и когда происходят сбои.
- Наличие логов упростит анализ инцидентов, повысит прозрачность и снизит потери из-за невыясненных причин отказов.
- Систематизированные логи можно использовать для построения автоматического алертинга и мониторинга.
- Внедрение логирования даст возможность быстрее масштабировать систему, не теряя управляемость.

Раздел: Необходимые логи и уровни

- Изменение статуса заказа (INFO): фиксировать время, ID заказа, ID клиента, предыдущий и новый статус, источник изменения (сервис).
- Ошибки взаимодействия с внешними API (ERROR): фиксировать метод, URL, код ответа, ID запроса.
- Системные сбои (FATAL): отказ подключения к БД, падение сервиса.
- Потерянные или дублирующиеся сообщения RabbitMQ (WARN).
- Начало и завершение расчёта стоимости (INFO): ID заказа, продолжительность.
- Неудачные попытки авторизации пользователей (WARN).
- Тайм-ауты на внешние запросы (ERROR).
- Попытки создать заказ с некорректной 3D-моделью (INFO или WARN в зависимости от частоты).

Системы, с которых требуется сбор логов:

- Онлайн-магазин (Java Spring Boot)
- CRM (Java Spring Boot)
- MES (C# backend)
- RabbitMQ (интеграционный уровень)
- Фронтенд приложений (по возможности)

Используемые уровни логирования:

- INFO — для штатных бизнес-событий
- WARN — для нестандартных ситуаций, которые не мешают работе, но требуют внимания
- ERROR — для ошибок, которые не нарушают выполнение сервиса, но требуют устранения
- FATAL — для ошибок, приводящих к остановке работы

Приоритет в логировании и трейсинге:

- В первую очередь: MES (из-за жалоб операторов), CRM (из-за проблем с заказами), RabbitMQ (из-за риска потерь сообщений)
- Второй приоритет: Онлайн-магазин и фронтенды

Раздел: Предлагаемое решение

- Будет использоваться стек OpenSearch + Logstash + Filebeat
- Все сервисы на Java и C# будут писать структурированные логи в stdout/stderr или в файл
- Filebeat будет установлен на каждом хосте и отправлять логи в Logstash
- Logstash выполнит парсинг логов и передаст их в OpenSearch
- Kibana будет использоваться для визуализации и поиска по логам
- Все логи будут в формате JSON

Политика безопасности:

- Доступ к логам будет предоставляться только через Kibana
- В Kibana будут заведены роли: read-only для поддержки и аналитиков, read-write только для DevOps
- Логи с персональными данными будут либо анонимизированы, либо исключены

Политика хранения:

- INFO-логи будут храниться 30 дней
- WARN/ERROR — 60 дней
- FATAL — 90 дней
- Будет использоваться ротация индексов (daily) и ILM-политики

Анализ логов:

- Будет реализован алертинг через Kibana или интеграцию с Alertmanager
- Примеры алертов: более 10 ошибок при расчёте стоимости за 5 минут, потеря связи с RabbitMQ, превышение времени ответа MES > 5 сек в течение 3 минут
- Будет настроен детектор аномалий: резкий всплеск создания заказов (возможная атака или ошибка)
